# ProxyPilot для Windows — дизайн

Дата: 2026-08-30
Статус: согласован, готов к разбивке на план реализации

## 1. Задача

Портировать ProxyPilot на Windows. Исходная задача продукта не меняется:
корпоративный HTTP-прокси шейпит трафик, рядом стоит быстрый SOCKS5, но
значительная часть инструментов SOCKS не понимает — Claude Code (undici)
отвечает `UnsupportedProxyProtocol`. Решение прежнее: локальный
HTTP-CONNECT мост по постоянному адресу `127.0.0.1:3129`, у которого
переключается выход — SOCKS5, корпоративный HTTP-прокси или напрямую.
Клиенты видят один и тот же адрес, поэтому смена маршрута не требует их
перезапуска.

Дополнительно портируются две функции, приросшие к macOS-версии позже и
для нашей организации несущие:

- **статический IP в офисе** — доступы выданы на фиксированные адреса,
  без статики человек в офисе не работает; вне офиса тот же адрес из
  чужой подсети означает отсутствие сети;
- **split-tunnel OpenVPN** — доступ к внутреннему git и dev-серверам
  снаружи, без заворачивания всего трафика через офис.

### 1.1 Отличие от macOS-версии

Windows-версия — **самостоятельный продукт**, а не общий код с macOS.
macOS-версия (zsh + Swift) остаётся как есть и в рамках этой работы не
трогается. Rust дорогу к объединению не закрывает: если Windows-ядро
себя покажет, macOS переносится на тот же `core` вторым шагом, с заменой
модуля опознания сети. Это решение принимается позже и по факту, а не
авансом.

## 2. Ключевые решения и их обоснование

Четыре решения определяют всё остальное.

### 2.1 Rust

Продукт на девять десятых состоит из системной сантехники: удержание
долгоживущих соединений, реакция на смену сети, чтение конфигурации
адаптеров, правка системных настроек прокси, повышение прав, автозапуск.
UI — окно на одиннадцать полей.

`windows-rs` даёт полный первоклассный доступ к Win32 и COM, включая
Network List Manager, без ручного интеропа. Бинарь статический, рантайма
нет.

### 2.2 Свой мост вместо gost

**Это решение снимает примерно половину унаследованной сложности.**

Значительная часть логики macOS-версии существует только потому, что
gost — отдельный процесс:

| Что есть на macOS | Почему | Судьба на Windows |
|---|---|---|
| Трёхуровневый антифлаппинг (TTL 30/60/300/1800, переспрос через 0.3–0.4 с) | Смена режима перезапускает gost и рвёт все живые соединения | **Не нужен.** Маршрут меняется атомарно, живые соединения доживают по старому пути |
| Понижение закреплённого режима до `direct` при мёртвом апстриме | У gost таймаут набора зашит в 15 с и не настраивается | **Не нужно как защита.** Таймаут наш. Механизм остаётся, но как продуктовое поведение, а не костыль |
| `pgrep` по имени конфига, `bridge-gateway`, `kill -9` через 2 с | Супервизия чужого процесса | **Не нужна** |
| Генерация YAML построчной печатью | Конфиг для внешнего процесса | **Не нужна** |
| Скачивание 25 МБ бинаря, прибитые SHA-256, склейка `lipo`, переподпись | gost не коммитится в репозиторий | **Не нужно.** Один exe без внешних зависимостей |
| Собственный список DNS-серверов для gost | Системный резолвер macOS терял живые домены (762 промаха за 2 часа) | **Не переносится.** Это болезнь macOS; используем системный резолвер |

Цена решения: мы владеем кодом, через который идёт весь трафик машины.
gost проверен годами, наш мост — нет. Отсюда требования к тестированию в
разделе 9.

### 2.3 Опознание офиса через Network List Manager

macOS не имеет понятия «сеть как объект», поэтому там пришлось строить
эвристику: перебрать `en*`-интерфейсы, взять адрес и шлюз, сверить
строковые префиксы, убедиться что шлюз отвечает за физическим
интерфейсом, пингануть, откатиться на ARP. Полторы сотни строк, и вся
конструкция существует ради того, чтобы поднятый VPN не сошёл за офис.

Windows держит реестр сетей: у каждой есть GUID, имя, категория
(Domain/Private/Public) и состояние. Сравнение по GUID не подделывается
туннелем, не ломается при смене подсети, не требует ни ICMP, ни ARP.

**Вся эвристическая половина не портируется.**

### 2.4 Туннель через установленный OpenVPN GUI

На машинах уже стоит OpenVPN GUI с драйвером и профилями. Своими силами
поднимать туннель нельзя: запущенный из командной строки под обычным
пользователем `openvpn.exe` **не использует OpenVPN Interactive Service,
и добавление маршрутов проваливается**. Интерактивная служба
задействуется только при запуске через `openvpn-gui.exe`.

Поэтому мы не поднимаем туннель, а дирижируем установленным клиентом:
кладём в его каталог конфигураций собранный split-tunnel профиль и
управляем им через `openvpn-gui.exe --command connect|disconnect`.

Следствия: не нужен свой демон, не нужен драйвер, **не нужны права
администратора для туннеля**, и мы не конфликтуем с их GUI — ручное
подключение к существующим профилям продолжает работать.

## 3. Архитектура

```
┌── ПОЛЬЗОВАТЕЛЬСКИЙ КОНТЕКСТ (без UAC) ─────────────────────┐
│                                                            │
│  ui        трей, окно настроек, bench, doctor              │
│    │                                                       │
│  core      режимы, решение auto, bypass-матчер, модель     │
│            конфига — чистая логика, ни одного системного   │
│            вызова, тестируется целиком                     │
│    │                                                       │
│    ├── bridge   tokio: HTTP CONNECT + обычный HTTP,        │
│    │            коннекторы socks5 / http / direct,         │
│    │            атомарная смена маршрута                   │
│    │                                                       │
│    ├── winnet   NLM (опознание сети + события),            │
│    │            WinINET в реестре, IP Helper               │
│    │                                                       │
│    └── vpn      сборка split-tunnel профиля,               │
│                 управление через openvpn-gui               │
└────────────────────────────────────────────────────────────┘
┌── SYSTEM (один UAC при установке, только если нужна статика) ─┐
│  profile   служба: статика ↔ DHCP по событию смены сети       │
└───────────────────────────────────────────────────────────────┘
```

Главное свойство раскладки: **`core` не знает ни про Windows, ни про
сокеты.** Всё, что трогает систему, живёт за узкими трейтами
(`NetworkInfo`, `SystemProxy`, `TunnelControl`), которые в тестах
подменяются. На macOS логика и вызовы утилит перемешаны в одном скрипте,
и проверить можно было только смоуком; здесь все выстраданные правила
становятся чистыми функциями с табличными тестами.

Второе свойство: **ядро не требует прав администратора.** Прокси в
WinINET — это `HKCU`. Чтение NLM — без прав. Слушатель на loopback — без
прав и без диалога брандмауэра. Туннель — через интерактивную службу
OpenVPN. Единственный UAC — установка службы профиля, и только если
статика нужна.

## 4. Модуль `core`

Чистая логика, без ввода-вывода.

### 4.1 Модель

```rust
enum Mode { Socks, Http, Direct, Auto }                     // сохранённое предпочтение
enum Route { Socks(SocketAddr), Http(SocketAddr), Direct }  // фактический выход

struct Health { socks: Reachability, http: Reachability }   // Up | Down | Unknown
struct Place  { in_office: bool, network: Option<NetworkId> }
```

### 4.2 Решение маршрута

```
decide(mode, place, health) -> Route

Auto   → если не в офисе                      → Direct
         иначе socks задан и жив              → Socks
         иначе http задан и жив               → Http
         иначе                                → Direct
Socks  → жив → Socks, иначе Direct (с пометкой «понижено»)
Http   → жив → Http,  иначе Direct (с пометкой «понижено»)
Direct → Direct
```

Правило «вне офиса — всегда напрямую» переносится дословно вместе с
обоснованием: снаружи через VPN офисный прокси тоже отвечает, но гонять
через него весь веб значит делать круг через офис; до офисных адресов
трафик и так идёт в туннель по маршрутам и мимо моста по bypass-списку.

Понижение до `Direct` при мёртвом апстриме сохраняется как продуктовое
поведение (пользователь не остаётся без сети), но **сохранённое
предпочтение не меняется** и возвращается само. В UI это показывается
явно: «SOCKS5 недоступен → работаем напрямую» — молчаливый обход был бы
непонятен.

### 4.3 Проверка живости

Дешёвый TCP-connect с таймаутом 1 с, кэш на 30 с. Нужен для решения
`Auto` и для индикаторов в окне настроек.

Вся машинерия против флаппинга (асимметричные TTL, повторные пробы,
подтверждение перехода) **не переносится**: она защищала от разрыва
соединений при перезапуске моста, а перезапуска больше нет.

### 4.4 Bypass-матчер

Переносится семантика macOS-версии: точное имя хоста, суффикс с точкой
(`.local`), IPv4-CIDR, IP-литералы, `localhost`.

Правило живёт **в мосте, а не в клиентах** — это осознанное решение
macOS-версии, и оно остаётся верным: Node/Bun и python-requests не
понимают CIDR, а часть приложений перетирает `NO_PROXY` своим списком.
Мост — единственное место, где список гарантированно соблюдается.

## 5. Модуль `bridge`

### 5.1 Слушатель

Привязка **строго к `127.0.0.1`**, никогда к `0.0.0.0` — иначе мы
открытый прокси для всей локальной сети. Порт из конфига, по умолчанию
3129.

### 5.2 CONNECT

Разобрать строку запроса и заголовки до `CRLFCRLF`, извлечь `host:port`,
прогнать через bypass, набрать через выбранный коннектор, ответить
`HTTP/1.1 200 Connection established`, дальше `copy_bidirectional`.

### 5.3 Обычный HTTP

Запрос в absolute-form (`GET http://host/path HTTP/1.1`). При апстриме
`http` проксируется почти как есть; при `socks5` и `direct`
переписывается в origin-form, набирается соединение к origin, ответ
транслируется обратно.

**Упрощение v1: keep-alive для обычного HTTP не поддерживается**, ответ
получает `Connection: close`. Подавляющая часть трафика — HTTPS через
CONNECT; усложнять v1 ради `http://` не стоит. Если окажется больно —
отдельной задачей.

### 5.4 Коннекторы

- **direct** — резолв системным резолвером, обычный TCP.
- **socks5** — рукопожатие без авторизации (`05 01 00`), команда CONNECT
  с **именем хоста**, а не с адресом (семантика `socks5h`): резолвит
  апстрим, что важно для внутренних имён.
- **http** — CONNECT к вышестоящему прокси, проброс ответа.

**Авторизация на апстриме в v1 не поддерживается** — в текущем конфиге
её нет. Если появится, добавляется отдельно и требует решения о хранении
секрета: сейчас продукт не хранит секретов вообще, и это свойство ценно.

### 5.5 Атомарная смена маршрута

Текущий маршрут живёт в `ArcSwap<Route>`. Каждое **новое** соединение
читает актуальное значение; **установленные соединения не трогаются** и
доживают по старому пути.

Это центральное свойство всей переработки: именно оно удаляет
антифлаппинг, и именно оно должно быть покрыто тестом (см. 9.2).

### 5.6 Таймауты и лимиты

- набор — 3 с (наш, настраиваемый; не 15 с, как было зашито в gost);
- чтение заголовков запроса — 10 с;
- **таймаута простоя нет**: туннель может легитимно молчать
  (long-poll, websocket, ssh); полагаемся на TCP;
- ограничение одновременных соединений — 512, сверх лимита клиент
  получает `503`.

### 5.7 Ошибки

Ошибка набора апстрима отдаётся клиенту как `502` с внятным телом (какой
апстрим, какая ошибка) и пишется в лог. Молчаливого перехода на `direct`
для отдельного соединения **нет**: это утечка трафика мимо выбранного
маршрута. Смена маршрута — только через решение `core`.

## 6. Модуль `winnet`

### 6.1 Опознание сети

`INetworkListManager::GetNetworks(NLM_ENUM_NETWORK_CONNECTED)`, для
каждой `INetwork` — `GetNetworkId()` (GUID), `GetName()`,
`GetCategory()`, `IsConnectedToInternet()`.

Офис = GUID входит в настроенный список. Список, а не одно значение:
площадок может быть несколько, и добавление новой в UI — кнопка «эта
сеть — офис», а не ввод префиксов руками.

### 6.2 События смены сети

Подписка на события NLM через точку подключения (`INetworkEvents`,
`INetworkListManagerEvents`). Резервный канал — `NotifyIpInterfaceChange`
из IP Helper. Опрос по таймеру не используется.

### 6.3 Системный прокси

`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`:
`ProxyEnable`, `ProxyServer`, `ProxyOverride`; применение немедленно
через `InternetSetOption(INTERNET_OPTION_SETTINGS_CHANGED / REFRESH)`.

Это **улучшение против macOS-версии**, где пользователю предписано
выставить системный прокси руками один раз. Здесь прав не нужно, поэтому
приложение управляет им само: включает при подъёме моста, снимает при
выходе, восстанавливает прежнее значение. В настройках — тумблер «не
трогать системный прокси» для тех, кто настраивает окружение сам.

**Восстановление после аварийного завершения.** Если процесс упадёт, в
реестре останется указатель на мёртвый слушатель, и пользователь
останется без сети вообще — отказ хуже того, который мы лечим. Поэтому:
прежнее значение сохраняется в конфиг **до** записи в реестр, и при
старте приложение проверяет, не осталось ли с прошлого запуска нашего
адреса при неподнятом мосте; если да — либо поднимает мост, либо
восстанавливает сохранённое значение. Это же проверяется в `doctor`
отдельным пунктом.

**Что этим не покрывается** (документируем честно, подсказкой в UI):

- **WinHTTP** (`netsh winhttp`) — контекст служб, требует администратора,
  в v1 не трогаем;
- **Firefox** — собственные настройки прокси, мимо WinINET;
- приложения, читающие `HTTP_PROXY` из окружения, — для них команда
  `proxypilot env` печатает готовые `set` / `$env:`.

### 6.4 Адаптеры и маршруты

`GetAdaptersAddresses` — адреса, шлюзы, DNS. `GetBestRoute2` — маршрут по
умолчанию. Адаптер для применения статики берётся **из NLM-подключения к
офисной сети**, а не из имени сервиса, как на macOS (там
`NET_SERVICE="Wi-Fi"`): док-станции и вторая сетевая карта перестают быть
проблемой.

## 7. Модуль `profile` — статический IP

Единственная часть, требующая администратора.

### 7.1 Форма

Служба Windows от LocalSystem, ставится один раз с одним запросом UAC
(`proxypilot.exe install-profile-service`). Подписывается на смену сети и
применяет профиль. Приложение общается с ней через именованный канал:
«применить сейчас», «дай состояние».

Служба выбрана вместо задачи планировщика: нужна точка, у которой можно
спросить состояние, и предсказуемое поведение при гонке событий.

### 7.2 Логика

```
сеть опознана как офис  → статический IP + офисные DNS
любая другая сеть       → DHCP
```

Применение — `netsh interface ipv4 set address` / `set dnsservers` на
адаптере офисного подключения.

### 7.3 Защита

Сохраняется страховка macOS-версии: после применения статики проверяется
достижимость шлюза, при неудаче — откат в DHCP с записью в лог.

На Windows риск качественно ниже (сеть опознана по GUID, а не по
совпадению префикса, так что выставить офисный адрес в чужой сети
практически невозможно), но откат стоит дёшево и остаётся.

Статика применяется **только если адрес настроен**. Пустое поле — сетью
не управляем, как на macOS.

### 7.4 Чья конфигурация

Служба читает не пользовательский файл, а свою копию профиля в
`%ProgramData%\ProxyPilot\profile.toml`, которую приложение пишет при
сохранении настроек. Это чище приёма macOS-версии, где демону
передавался `XDG_CONFIG_HOME` пользователя, и снимает вопрос о правах на
пользовательский файл.

## 8. Модуль `vpn`

### 8.1 Сборка split-tunnel профиля

Из исходного `.ovpn` собирается новый, рядом в каталоге конфигураций
OpenVPN, под отдельным именем (`proxypilot-office`), чтобы не трогать
существующие профили:

- `pull-filter ignore "redirect-gateway"` — сервер обычно пушит маршрут
  по умолчанию и **не** пушит маршруты в офисные подсети, то есть без
  правки весь трафик, включая видео, идёт кругом через офис;
- явные `route` в офисные сети. Подсеть, где машина стоит физически, не
  страдает: её собственная запись в таблице маршрутов точнее.

### 8.2 Осознанное расхождение с macOS: DNS

macOS-версия добавляет `pull-filter ignore "dhcp-option DNS"`, оставляя
резолвер домашним. **Здесь мы этого не делаем и пушенный DNS
принимаем.**

Причина: назначение туннеля — доступ к внутреннему git и dev-серверам,
то есть к внутренним именам. Без офисного DNS они не резолвятся, и
функция теряет смысл. Офисный DNS-сервер доступен через туннель по
добавленным маршрутам.

Плата: пока туннель поднят, все DNS-запросы идут в офис. Если это станет
проблемой, точечное решение на Windows — NRPT
(`Add-DnsClientNrptRule`), маршрутизация DNS по доменным зонам. В v1 не
делаем.

### 8.3 Управление

`openvpn-gui.exe` и каталог конфигураций находятся через реестр
(`HKLM\SOFTWARE\OpenVPN`). Подъём и останов —
`--command connect|disconnect proxypilot-office`.

Если OpenVPN не установлен — раздел VPN в UI неактивен с внятным
объяснением. Своего клиента и своего драйвера мы не ставим.

### 8.4 Чужой туннель

Если маршрут в офисные подсети уже лежит через туннельный адаптер,
поднятый не нами (человек подключился руками через их GUI), — не
вмешиваемся ни в подъём, ни в останов, и показываем это в меню.

Критерий именно такой, а не «есть любой tun-адаптер с адресом»:
постоянно поднятый Tailscale или WireGuard не должен блокировать офисный
туннель. Логика переносится из macOS-версии дословно.

### 8.5 Автоматика

При включённом тумблере: вне офиса — поднять, в офисе — опустить. По
умолчанию выключено, туннель поднимается руками.

### 8.6 Возможное упрощение: SOCKS5 через SSH вместо туннеля

Своего туннеля мы не пишем осознанно: дальний конец не наш — в офисе
стоит OpenVPN-сервер админов, с сертификатами на конкретных людей. «Свой
туннель» означало бы «своя реализация клиента OpenVPN», то есть месяцы
работы над криптокодом, несущим корпоративные учётки, без всякой пользы
продукту. С мостом ситуация обратная (SOCKS5 — протокол на полстраницы,
секретов не трогаем), поэтому его писать стоило, а клиент VPN — нет.

Но у задачи есть более простая формулировка. Туннель нужен ради доступа
к внутреннему git и dev-серверам, то есть ради **соединений к конкретным
хостам**, а не ради помещения всего ноутбука в офисную сеть. Механизм
ровно для этого у нас уже будет — мост с апстримом.

Если снаружи доступен SSH-бастион, то `ssh -D` поднимает SOCKS5 внутрь
офисной сети, и он вставляется в ProxyPilot как обычный апстрим —
кодом, который к тому моменту уже написан. Ни драйвера, ни клиента VPN,
ни маршрутов, ни возни с DNS.

**Проверить до начала этапа 6**: есть ли доступный снаружи SSH-хост и
допускает ли это политика. Если да — раздел 8 из первой версии
выкидывается целиком, вместе с зависимостью от OpenVPN и всей его
частью в UI. Если нет — делаем как описано выше.

## 9. Тестирование

Область, где Windows-версия обязана быть сильнее macOS-версии: там через
мост шёл проверенный годами gost, здесь — наш код.

### 9.1 `core` — табличные тесты

Полное покрытие: таблица решений `decide()` по всем сочетаниям режима,
места и живости; bypass-матчер (переносятся все случаи из
macOS-конфигов); вывод маршрутов из офисной подсети; вычисление маски из
длины префикса — на macOS здесь был целый класс ошибок (`/14`
превращался в `/24`), и в CI на это стоял отдельный тест.

### 9.2 `bridge` — интеграционные тесты

Поднимаются локальные фальшивки: SOCKS5-сервер, HTTP-прокси,
HTTP-origin. Проверяется:

- CONNECT через каждый коннектор, сквозная передача байтов;
- адрес из bypass-списка идёт напрямую, минуя апстрим;
- мёртвый апстрим → `502` клиенту, а не зависание;
- соблюдение таймаута набора;
- **смена маршрута не разрывает установленное соединение** — ключевое
  свойство, ради которого затевался свой мост: открыть CONNECT, начать
  передачу, переключить маршрут, убедиться что поток цел и что *новое*
  соединение пошло уже по новому пути;
- превышение лимита соединений → `503`, а не исчерпание ресурсов.

### 9.3 Платформенные модули

`winnet` и `vpn` закрыты трейтами и в тестах `core` подменяются. Плюс
несколько смоук-тестов на реальной Windows в CI: прочитать список сетей,
прочитать и вернуть обратно настройки прокси в реестре, найти OpenVPN.

### 9.4 CI

GitHub Actions, `windows-latest`: `cargo test`, `cargo clippy -D
warnings`, `cargo fmt --check`, сборка релиза, выгрузка артефакта.

## 10. Конфигурация и файлы

- `%APPDATA%\ProxyPilot\config.toml` — TOML через `serde`. Формат
  `KEY=VALUE` был продиктован тем, что файл читал шелл; здесь этого
  ограничения нет. Свойство безопасности macOS-версии («конфиг не
  исполняется, иначе строка пользователя стала бы root-командой»)
  достаётся бесплатно.
- `%ProgramData%\ProxyPilot\profile.toml` — копия для службы (см. 7.4).
- `%LOCALAPPDATA%\ProxyPilot\logs\` — логи **с ротацией**; на macOS
  ротации нет, это исправляем.

Состав конфигурации: порт моста, апстримы socks/http, список офисных
сетей (GUID + имя для отображения), bypass-список, URL и объём для
`bench`, тумблер управления системным прокси, профиль статики (адрес,
маска, DNS), настройки VPN (исходный профиль, маршруты, автоматика).

## 11. UI

### 11.1 Трей

`tray-icon` + оконный цикл сообщений. Иконка отражает активный маршрут
(socks / http / direct / мост не запущен / не настроено). Меню повторяет
macOS-версию: заголовок с адресом моста и текущим состоянием,
переключение режимов с индикаторами доступности, секция сети и туннеля
(показывается только когда настроена), замер скорости, диагностика,
копирование адреса, настройки, выход.

### 11.2 Окно настроек

Основной вариант — `native-windows-gui`: нативные виджеты, родной вид,
одиннадцать полей и тумблер укладываются без напряжения.

Запасной ход, если NWG окажется болезненным: отдавать страницу настроек
на отдельном loopback-порту (со случайным токеном в URL, слушатель
поднимается только на время открытого окна) и открывать её в браузере
пользователя. Асинхронный стек для этого уже есть, но это именно второй
слушатель — не тот, что обслуживает прокси. Критерий переключения: форма
не собирается за разумное время либо ломается на DPI и темах.

Вывод `bench` и `doctor` — как на macOS, отдельным окном с моноширинным
текстом.

## 12. Поставка

- Один `.exe`, `x86_64-pc-windows-msvc`; `aarch64` — по потребности.
- **Подпись Authenticode обязательна.** Неподписанный exe, который
  открывает слушающий сокет и правит ключи прокси в реестре, —
  учебниковый профиль малвари; SmartScreen и эвристики антивирусов
  реагируют охотно. Единственный пункт, требующий закупки (сертификат
  OV/EV) и решения вне инженерной плоскости.
- Установщик для ядра **не нужен**: скачал exe, запустил, работает.
  Отдельная команда ставит службу профиля (с UAC) — только тем, кому
  нужна статика.
- Автозапуск — `HKCU\...\Run`, тумблером в настройках.
- Обновления — проверка релизов на GitHub, замена бинаря.
  Дифференциальных обновлений не делаем.

## 13. Не-цели

- Общий код с macOS-версией в этой итерации.
- Авторизация на апстрим-прокси (логин/пароль).
- PAC-файлы, WPAD, автоконфигурация прокси.
- Прокси в контексте служб (WinHTTP) и автонастройка Firefox.
- Установка своего OpenVPN и драйвера.
- IPv6-апстримы (сам мост IPv6-литералы в CONNECT обрабатывает).
- Дифференциальные обновления.

## 14. Риски и открытые вопросы

| Риск | Оценка | Что делаем |
|---|---|---|
| Свой мост в бою хуже gost | Основной риск проекта | Тесты 9.2, особенно на смену маршрута и утечки ресурсов; постепенное внедрение |
| Нет сертификата подписи | Высокий, блокирует раздачу | Решение по закупке нужно до релиза; до этого раздача внутри с ручным разрешением |
| `native-windows-gui` окажется неудобным | Средний | Заранее определён запасной ход (11.2) |
| Приём пушенного DNS отправляет все запросы в офис | Средний | Осознанное решение v1; при необходимости NRPT |
| Обычный HTTP без keep-alive окажется мало | Низкий | Отдельная задача, если проявится |
| OpenVPN GUI сменит интерфейс командной строки | Низкий | Версия проверяется при старте, деградация с внятным сообщением |

**Открытый вопрос:** сколько офисных сетей и появляются ли новые.
Спроектировано как список, поэтому на дизайн не влияет; влияет только на
удобство UI при первом заполнении.

## 15. Порядок работ

1. `core` + тесты — чистая логика, ни одного системного вызова.
2. `bridge` + интеграционные тесты — до всякого UI; проверяется через
   `curl -x`.
3. `winnet`: NLM, системный прокси, события.
4. Трей и переключение режимов — первая работающая сборка.
5. Окно настроек, `bench`, `doctor`.
6. `vpn`.
7. `profile` (служба, статика).
8. Подпись, автозапуск, обновления.

Пункты 1–4 дают самостоятельно полезный продукт, решающий исходную
задачу. 5–8 наращиваются поверх без переделки.
