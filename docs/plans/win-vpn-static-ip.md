# ProxyPilot Windows — план 4: туннель и статический адрес

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** закрыть офисную половину задачи — доступ к внутренним ресурсам снаружи через split-tunnel и фиксированный адрес в офисе, под который выданы доступы.

**Architecture:** туннель мы **не поднимаем сами** — мы дирижируем уже установленным у пользователя OpenVPN GUI. Статический адрес меняет отдельная служба Windows: смена IPv4 требует прав администратора, а ядро приложения обязано остаться беспарольным.

**Tech Stack:** Rust 2021, `windows` (реестр, служба, IP Helper), `windows-service` для службы. Никакого своего VPN-клиента и никаких драйверов.

**Spec:** [`docs/superpowers/specs/2026-08-30-proxypilot-windows-rust-design.md`](../specs/2026-08-30-proxypilot-windows-rust-design.md) — разделы 7 (статический IP) и 8 (туннель).

**Предыдущие планы:** [1](2026-08-30-proxypilot-win-core-bridge.md), [2](2026-08-30-proxypilot-win-winnet-tray.md), [3](2026-08-30-proxypilot-win-settings-bench-doctor.md).

## Два решения, которые определяют весь план

### Туннелем управляет их GUI, а не мы

`openvpn.exe`, запущенный из командной строки под обычным пользователем, **не задействует OpenVPN Interactive Service, и добавление маршрутов проваливается**. Интерактивная служба подключается только при запуске через `openvpn-gui.exe`. Поэтому:

- мы кладём собранный split-tunnel профиль в каталог конфигураций OpenVPN под **отдельным именем** (`proxypilot-office`), не трогая существующие профили пользователя;
- поднимаем и опускаем его через `openvpn-gui.exe --command connect|disconnect`;
- не ставим ни своего клиента, ни драйвера.

Следствие: **прав администратора для туннеля не требуется вовсе**, и мы не деремся с их GUI — ручное подключение к своим профилям продолжает работать.

Если OpenVPN не установлен, раздел туннеля в UI неактивен с внятным объяснением. Мы не предлагаем его поставить и тем более не ставим сами.

### Статический адрес меняет служба

Смена IPv4 в Windows доступна только администратору. Ядро приложения обязано остаться без единого запроса UAC — это свойство, за которое мы держались все три плана. Поэтому статика живёт в отдельной службе, которая ставится **один раз, с одним запросом UAC, и только если статика нужна**. Кому она не нужна — тот не видит ни одного диалога.

Служба читает **свою** копию профиля в `%ProgramData%\ProxyPilot\profile.toml`, которую пишет приложение. Не пользовательский файл: служба работает от LocalSystem, а файл в профиле пользователя правится самим пользователем, и читать его от системной учётной записи — значит открывать дорогу к подмене.

## Global Constraints

Первые пять унаследованы и остаются в силе.

- Слушатель моста привязывается **строго к `127.0.0.1`** и **один раз за жизнь процесса**.
- **`Router::get()` имеет ровно одну не-тестовую точку вызова** и ровно одного не-тестового писателя.
- **Любой путь завершения процесса восстанавливает системный прокси.**
- **Ядро приложения не показывает UAC.** Единственный запрос прав во всём продукте — установка службы профиля, и он явный, однократный и необязательный.
- Изменения настроек идут единственным путём — через канал `Cmd`.
- **Мы не ставим стороннее ПО и не трогаем чужие профили OpenVPN.**
- Rust edition 2021, `rust-version = "1.75"`; три проверки CI.
- Комментарии объясняют **почему**, по-русски.

### Task 1: Поиск установленного OpenVPN

**Files:** `win/crates/winnet/src/openvpn.rs`, `win/crates/winnet/src/lib.rs`

**Produces:** `Installation { gui_exe: PathBuf, config_dir: PathBuf }`, `find_installation() -> Result<Option<Installation>, WinNetError>`.

### Task 2: Сборка split-tunnel профиля

**Files:** `win/crates/winnet/src/ovpn_profile.rs`

**Produces:** `build_profile(source: &str, routes: &[Ipv4Net]) -> String`, `mask_of(bits: u8) -> Ipv4Addr`, `default_routes(office_networks: &[..]) -> Vec<Ipv4Net>`.

**Что делаем с исходным профилем и почему:**

- `pull-filter ignore "redirect-gateway"` — сервер обычно пушит маршрут по умолчанию и **не** пушит маршруты в офисные подсети. Без этой строки в туннель уходит весь трафик, включая видео, кругом через офис.
- явные `route` в офисные сети. Подсеть, где машина стоит физически, не страдает: её собственная запись в таблице маршрутов точнее любого `/16`.
- **пушенный DNS принимаем** — и это осознанное расхождение с macOS-версией, где от него отказываются. Назначение туннеля здесь — внутренний git и dev-серверы, то есть внутренние имена; без офисного DNS они не резолвятся и функция теряет смысл. Плата: пока туннель поднят, все DNS-запросы идут в офис. Записать это в комментарий и показать в UI.
- вычистить `setenv opt block-outside-dns` — директива только для Windows-сборок другого клиента, наша ругается на неё при каждом старте.

**Маска считается арифметикой из длины префикса, а не таблицей.** На macOS здесь был целый класс ошибок: `/14` молча превращался в `/24`. Тест на `/1`, `/14`, `/24`, `/32` обязателен.

- [ ] Тесты: маска из битов для всех граничных значений; профиль содержит `pull-filter` и все маршруты; исходные строки не потеряны; `block-outside-dns` вычищен; пушенный DNS **не** отфильтрован.
- [ ] Коммит: `feat(win): сборка split-tunnel профиля`.

### Task 3: Чужой туннель

**Files:** `win/crates/winnet/src/tunnel_state.rs`

**Produces:** `our_tunnel_up(...) -> bool`, `foreign_tunnel_up(routes: &[Ipv4Net], adapters: &[AdapterRoute]) -> bool`.

**Критерий — не «есть ли туннельный адаптер», а «лежит ли уже маршрут в наши офисные сети через чужой туннель».** Разница принципиальная: у пользователей Tailscale или WireGuard туннельный адаптер поднят постоянно, и наивная проверка не дала бы поднять офисный туннель никогда. Логика переносится из macOS-версии дословно — там она такая по той же причине.

Если чужой туннель в наши сети уже поднят — **не трогаем ни поднятие, ни опускание** и показываем это в меню. Два туннеля разом дерутся за маршруты.

- [ ] Тесты чистые, на подставных таблицах маршрутов: постоянный Tailscale не считается чужим; туннель с маршрутом в офисную сеть считается; наш собственный не считается чужим.
- [ ] Коммит: `feat(win): распознавание чужого туннеля по маршрутам`.

### Task 4: Управление туннелем

**Files:** `win/crates/winnet/src/openvpn.rs`

**Produces:** `install_profile(&Installation, name: &str, contents: &str)`, `connect(&Installation, name) `, `disconnect(&Installation, name)`, `status(...)`.

Запуск строго через `openvpn-gui.exe --command …`. Профиль кладём под своим именем; **существующие профили пользователя не читаем, не перемещаем и не переименовываем** — только исходный, который пользователь сам указал как источник.

- [ ] Тесты на формирование командной строки и на отказ, когда OpenVPN не найден.
- [ ] **Ручная проверка обязательна** и требует человека: поднять туннель из приложения, убедиться что внутренний ресурс доступен, а внешний трафик идёт мимо (сравнить внешний IP при поднятом туннеле — он должен остаться домашним), опустить.
- [ ] Коммит: `feat(win): подъём и останов туннеля через OpenVPN GUI`.

### Task 5: Профиль сети — данные и решение

**Files:** `win/crates/core/src/netprofile.rs`

**Produces:** `NetProfile { office_ip, office_mask, office_dns, adapter }`, `decide_profile(place: &Place, profile: &NetProfile, current: &AdapterConfig) -> ProfileAction`, `ProfileAction { SetStatic{..}, SetDhcp, LeaveAlone }`.

Чистая логика, без ввода-вывода:

```
в офисе   → статический адрес и офисные DNS
не в офисе → DHCP
адрес не задан → не трогаем сеть вообще
адрес прописан не нами → не трогаем: это чужая настройка
```

Последняя строка важна: сбрасывать в DHCP статику, которую поставил не ты, — это ломать чужую конфигурацию.

- [ ] Тесты таблицей по всем сочетаниям; отдельно — «пустой адрес значит не управляем», «чужая статика не сбрасывается».
- [ ] Коммит: `feat(win): решение о профиле сети`.

### Task 6: Служба профиля

**Files:** `win/crates/netsvc/` (новый крейт-бинарь)

**Produces:** служба Windows `ProxyPilotNetProfile`, команды `install-service` / `uninstall-service` в приложении.

- Работает от LocalSystem, ставится один раз с одним UAC.
- Читает `%ProgramData%\ProxyPilot\profile.toml`, который пишет приложение.
- Подписывается на смену сети (тот же NLM) и применяет решение из задачи 5.
- Применение — `netsh interface ipv4 set address` / `set dnsservers` на адаптере **офисного подключения**, взятом из NLM, а не по имени сервиса: док-станции и вторая сетевая карта перестают быть проблемой. Это лучше, чем на macOS, где адаптер задавался строкой.
- **Страховка:** после применения статики проверить достижимость шлюза и при неудаче откатиться в DHCP с записью в лог. На Windows риск ниже (сеть опознана по GUID, а не по совпадению префикса), но откат стоит дёшево.

- [ ] Тесты на разбор конфигурации службы и на формирование команд; логика решения уже покрыта задачей 5.
- [ ] **Ручная проверка требует человека и офисной сети.** Первый живой прогон — при пользователе, а не в фоне: мы меняем сетевые настройки машины, и ошибка здесь стоит потери связи.
- [ ] Коммит: `feat(win): служба профиля сети`.

## Открытый вопрос, который стоит закрыть до задачи 4

Спека 8.6: если снаружи доступен SSH-бастион, то `ssh -D` даёт SOCKS5 внутрь офисной сети, и он вставляется в ProxyPilot как обычный апстрим — кодом, который уже написан. Ни драйвера, ни клиента, ни маршрутов, ни возни с DNS. Тогда задачи 1–4 не нужны вовсе.

Это вопрос к администраторам, а не к коду. Пока ответа нет, делаем через OpenVPN — он у пользователя работает и проверен.
